## Pre-walkthrough desk review (README + docs/00–06 + four template repos)

### 1. [HIGH] README's "Where to go next" contradicts 00-prerequisites.md on local tools
- **Observed:** README.md line 44: *"00-prerequisites.md — confirm your setup and **get TaskFlow running locally**, before touching Unify at all."* `00-prerequisites.md` itself says: *"**None required** ... You won't need Docker, Python, Node.js, or even git on your own machine to complete this lab."*
- **Issue:** These directly contradict each other. A participant reading only the README's module list would set up local tooling that Module 00 explicitly says is unnecessary — undermining the lab's core "no local tools" promise before Module 00 is even opened.
- **Proposed edit:** README.md line 44 → change to something like *"confirm your setup — no local tools required"* to match 00-prerequisites.md.

### 2. [HIGH] "Commit and push" instructions have no web-UI path — and this repeats across every workflow-creation step, not just Module 02
- **Observed:** Every module that has participants add a `.cloudbees/workflows/*.yaml` file ends the step with just "Commit and push" (or "Commit, push, and run"), with no instructions for doing this without local git:
  - 02-first-workflow.md Step 3 (`build.yaml` in taskflow-backend)
  - 03-multi-component-app.md Step 1, Step 2, Step 3, Step 7 (`build.yaml` ×2, `deploy.yaml` ×3, `deployer.yaml`)
  - 04-release-orchestration.md Step 1 (`release-wf.yaml`)
- **Issue:** This is the single biggest gap against the "browser + GitHub web UI only" constraint. It's not an isolated slip in one step — it's the standard closing instruction for every file-creation step in the lab, meaning the "no git" claim fails repeatedly, not once. A participant with no git installed has no path forward at any of these five points unless they already know GitHub's web "Add file > Create new file" flow and improvise it themselves.
- **Proposed edit:** Add one explicit, reusable sub-section (e.g. in 00-prerequisites.md or 01-orientation.md) titled something like "Creating and editing files without git," documenting the GitHub web UI flow (Add file → Create new file → paste YAML → Commit directly to the `main` branch) once, and have every later "Commit and push" step link back to it instead of repeating an assumption of local git.

### 3. [MED] 00-prerequisites.md references a "signpost" repo participants are already inside
- **Observed:** 00-prerequisites.md line 18: *"Your facilitator will point you to a 'signpost' repo with links to four GitHub template repositories."* This document *is* that signpost repo (or a module inside it) — but unlike README.md, it doesn't list the four repo links itself, only names them.
- **Issue:** A participant who lands on 00-prerequisites.md directly (e.g. via a shared module link, per the README's own suggestion at line 52 that facilitators may link docs directly rather than through the README) has no links to click — only repo names with no href.
- **Proposed edit:** Either link the four repos directly in 00-prerequisites.md (duplicating README's table), or explicitly state "these links are in README.md — go there first" with a link.

### 4. [LOW] `register-build-artifacts@main` unpinned while `checkout@v2` is pinned
- **Observed:** In every `build.yaml` template (02-first-workflow.md, 03-multi-component-app.md ×2): `uses: cloudbees-io/checkout@v2` (pinned) vs. `uses: cloudbees-io/register-build-artifacts@main` (unpinned, tracks the moving `main` branch). Same inconsistency for `publish-evidence-item@v1` and `register-deployed-artifact@v2` in `deploy.yaml` — both pinned — vs. `register-build-artifacts@main` again being the outlier.
- **Issue:** An unpinned action can change behavior under participants without warning, and it's inconsistent with the pinning convention used everywhere else in the same file. Low severity because it's CloudBees' own action in a workshop context, but worth a fix for lab stability and to model good practice for participants who'll copy this YAML into real pipelines.
- **Proposed edit:** Pin to a specific released tag, matching the other three actions.

### 5. [MED] Module 02 Step 1 ("Connect your GitHub account/org") is one line for what may be the biggest friction point
- **Observed:** 02-first-workflow.md Step 1: two bullets total — "Sign in... Connect your GitHub account/org if you haven't already (one-time setup)."
- **Issue:** No screenshots, no mention of what OAuth/GitHub App permission screens look like, no guidance on org-level app-install approval (which may require a GitHub org owner's approval for participants using a personal account against an org, or may itself be blocked for participants who only have a personal GitHub account and no org). For a workshop with external, unfamiliar-with-Unify participants, this is exactly the kind of step likely to eat 10+ minutes of facilitator time if underspecified. Needs to be verified live — flagging now as a predicted risk, to confirm or dismiss when we reach Module 02.
- **Proposed edit:** Pending live walkthrough — likely needs a screenshot-backed sub-sequence.

### 6. Two facts verified directly (no longer open questions)
- **(a) README item 7 link text vs. href vs. actual file:** README.md line 50 renders as `[06-wrap-up-next-steps.md](docs/06-wrap-up.md)`. The actual file in the repo is `docs/06-wrap-up.md` — the **href is correct**; the **link text is stale/wrong** (it doesn't match the href *or* the real filename). Same stale name appears again at the bottom of 05-feature-flags.md line 117: `Next: [06-wrap-up-next-steps.md](06-wrap-up.md)`.
  - **Proposed edit:** Fix link text in both README.md and 05-feature-flags.md to read `06-wrap-up.md`.
- **(b) Does taskflow-backend already ship `.cloudbees/workflows/build.yaml`?** No. None of the four template repos (`taskflow-frontend`, `taskflow-backend`, `taskflow-db`, `app-taskflow`) contain a `.cloudbees/` directory at all — confirmed by a full file listing of each. Every workflow file in Modules 02–04 is genuinely created from scratch by the participant, matching what the docs claim. No action needed here — this is a pass, not a finding.

### 7. [MED] 05-feature-flags.md references source paths that don't exist in the actual repo
- **Observed:** 05-feature-flags.md Step 2 says "Open `app/backend/flags.py`" and later "see `app/frontend/src/App.jsx`." The actual `taskflow-backend` repo has `flags.py` at repo root (no `app/` prefix at all — not even `backend/`), and `taskflow-frontend` has `src/App.jsx` at repo root (no `app/frontend/` prefix).
- **Issue:** A participant following the doc literally, either browsing GitHub's web UI or reading locally, will not find `app/backend/flags.py` — it doesn't exist at that path. Minor confusion but a direct claim that doesn't hold up.
- **Proposed edit:** Change references to `flags.py` and `src/App.jsx` (matching actual repo root layout), or restructure the repos to match the doc if the `app/` nesting was intentional for some other reason.

### 8. [LOW] app-taskflow's own README describes files that don't exist yet at copy-time
- **Observed:** `app-taskflow/README.md` states in the present tense that the repo "holds" `.cloudbees/workflows/deployer.yaml` and `release-wf.yaml` — but per finding #6(b), the repo (and thus every participant's copy of it) ships with only a `README.md`; those two workflow files are created later, by the participant, in Module 03 Step 7 and Module 04 Step 1.
- **Issue:** Minor — could read as the repo already containing those files when a participant first opens their copy, right after Module 03 Step 5 explicitly tells them to go check this README for confirmation the repo copied correctly.
- **Proposed edit:** Reword to future/prescriptive tense, e.g. "...exists to hold the workflows you'll add in Modules 03–04:" to avoid implying they're already present.
